# 远期项目：原生像素到显示面的低延迟交付

状态：规划中，未启动实现。建立日期：2026-09-13。

## 目标与边界

减少完整图已经解码后，为了显示而重复执行 JPEG 编码、整块字节交付和 JPEG 再解码的成本。
照片显示应尽早使用可用像素，持久化缓存不成为前景显示的前置条件。
先以 Windows / WIC 完整显影验证，再判断是否推广到其他解码器与平台。

这是远期架构项目，不是当前版本发布的新增阻断项，也不预先决定采用 D3D。
先证明收益，再选择共享像素画布或原生渲染面；两条路线不要求都产品化。

现有相机 JPEG 直通继续优先使用，不为统一显示架构强制 CR3 / RW2 走 RAW 显影。
保留像素尺寸、方向、颜色与细节；未经官方解码结果对比验证，不增加锐化、降噪或对比度
处理。现有显示锐化仅适用于已验证的 Sony HIF。

## 基线必须重测

[CR3/RW2 实测报告](../research/raw-jpeg-delivery-2026-09-13.md)中的约 496 ms，是旧 WIC
锐化输出从 URL 提交到解码就绪的历史数据，不是 JSON RTT，也不是实际 GPU present。
额外 RAW 锐化已删除；移除后同一文件原生管线单次约 3137 ms，但未重测完整 UI 交付。
因此本项目必须先测当前无额外后处理的实现，不能把旧 496 ms 当作新方案对照基线。

## 阶段与决策门槛

| 阶段 | 工作与交付物 | 通过条件 |
| --- | --- | --- |
| A：建立基线 | 当前 Release 的分阶段跟踪、真实文件矩阵、内存与帧时间报告、可重复运行的比较脚本 | 区分解码、交付、绘制、缓存成本，确定设备与场景基线 |
| B：共享像素原型 | WIC 像素通过 WebView2 shared buffer 交给 Canvas/WebGL；先实现单张显示、替换和释放 | 同输入证明收益，像素/颜色/方向正确，内存有界 |
| C：架构选择 | 根据 B 的剩余成本，按需制作原生 D3D 图片渲染面原型，输出比较报告与 ADR | 对延迟、内存、交互和维护成本作出采用或停止决定 |
| D：产品集成 | 接入 loupe、优先级、取消、资源生命周期与后台缓存；增加能力检测和运行时回退 | 快速切图、缩放拖动、窗口变化、清缓存及故障恢复通过 |
| E：发布验证 | 打包应用的设备矩阵、长时间稳定性、性能回归门槛；其他平台单独评估 | 验收目标稳定满足，已有浏览/缩略图/相机 JPEG 路径无回归 |

### A：测量方法

- 分别记录请求排队、RAW 解码结束、颜色/方向准备结束、资源交付、GPU 上传、首帧实际
  呈现、完整细节呈现、后台缓存完成。跨进程时间需要校准或通过同一系统跟踪关联。
- 不用 `img.decode()` 完成、IPC 返回或纹理提交替代实际呈现。无法测得 present 时明确
  标注代理指标，不能据此宣告显示延迟目标通过。
- 固定同一解码器、输入像素、尺寸和颜色策略，对比当前 JPEG 交付、共享像素与原生渲染面。
  另报选中到完整图的总延迟，避免用排除解码的指标代替用户等待时间。
- 覆盖 24 MP 与高像素 RAW、横竖方向、ICC、连续切图。本地 SSD / NAS、应用冷/热缓存
  分开统计，说明 OS/NAS 缓存状态；主要场景至少各 30 次，报告中位数和 P95。
- 固定正式构建和视口，记录 CPU/GPU、驱动与 WebView2 版本。同时统计原生进程、WebView
  进程及 GPU 分配，避免把转移给 GPU 的内存成本当作消失。

### B：共享像素到 GPU 画布

验证 WebView2 共享缓冲到 JS ArrayBuffer 的能力和打包要求。原生写入完成后再发布，
浏览器按只读数据处理；跨层描述符明确尺寸、步长、像素格式、颜色、方向和 generation。
颜色变换只执行一次，画布颜色管理与当前受管 JPEG 路径对照。首阶段支持明确的 SDR/sRGB，
其他颜色状态使用已验证的回退路径。

分别计量缓冲填充、共享、GPU 上传和绘制。约 2400 万像素的 RGBA 本身接近 97 MB，
共享内存不等于零拷贝上屏，不以无限缓冲换取延迟。JPEG 缓存可在显示后异步编码，使用
有界后台任务，不能抢占新选中的图片；不需要持久化的产物避免只为旧显示流程生成 JPEG。

### C：原生 D3D 渲染面与选择

仅当 B 的纹理上传、WebView 调度或内存开销仍限制目标时，验证原生图片渲染面。
照片由原生图形层保存和绘制，WebView 负责控件与低带宽状态，像素不走 JSON。

原型必须处理与 WebView 的合成关系、遮挡、透明叠加、焦点与输入坐标、裁剪、DPI 和
窗口缩放。比较实际 UI 中的单张交付和持续缩放拖动，不以孤立原生窗口证明集成完成。
调查共享纹理能否减少 CPU 复制并实测确认，不预先宣称零拷贝。

ADR 明确采用共享像素、采用原生渲染面、保留当前 JPEG 路径或继续有限验证，并记录
跨平台成本。macOS / Linux 使用各自原生 API 独立评估，Windows D3D 不成为公共领域
模型或其他平台运行的前提。

### D：生命周期与约束

遵循[性能不变量](../PERFORMANCE_INVARIANTS.md)，保留源版本、generation、lease、取消、
优先级、已有预览、整目录缩略图保留和非阻塞诊断契约。

- 新图片准备期间保留有效预览；迟到像素或帧不能覆盖已切换的选择。
- 原生缓冲和 GPU 纹理有明确所有者、容量上限及释放时机。覆盖取消、关闭、WebView 重载、
  图形设备丢失和解码失败，不过早复用仍被 GPU 读取的缓冲。
- 保持 loupe 缩放、拖动、定位器、焦点叠加和方向坐标一致；就绪通知不能堵塞 UI。
- 保留当前交付路径用于能力缺失或运行故障的回退。这是运行能力回退；历史生成产物
  统一使用设置中的“清空缓存”，不增加针对过去错误的缓存兼容或遗留格式迁移分支。

## 验收目标与停止条件

以下是尚未验证的初始项目目标。A 阶段锁定基准设备和场景，不通过降低清晰度、关闭颜色
管理、取消解码等待或放宽指标宣告达成。

| 维度 | 目标 |
| --- | --- |
| 24 MP SDR 完整图交付 | 原生解码完成到完整图片实际呈现，中位数 ≤100 ms、P95 ≤200 ms；包括必要的方向/颜色准备与上传 |
| 改善幅度 | 同设备同像素，相对 A 的现有交付路径中位数至少降低 50%；另报选中到完整图时间 |
| 交互 | 固定 4K / 60 Hz 基准视口中，热缩放/拖动帧时间 P95 ≤16.7 ms，无持续空白或错图 |
| 内存与资源 | A 阶段固定各路线内存预算，B/C 集成前给出可执行上限；至少 300 次快速切图后占用稳定，无持续增长的缓冲、纹理或 lease |
| 图像正确性 | 尺寸、方向与已验证颜色参考一致，在预先规定容差内通过像素比较，无新增未经验证的后处理 |
| 浏览与恢复 | 保持已有目录、缩略图与相机 JPEG 性能预算；清缓存、取消、重载、设备丢失后可恢复 |

若 B/C 没有稳定收益、颜色正确性无法保证或内存/维护成本超出预算，停止该路线并记录
证据。更快的 SIMD JPEG 编码可作为独立优化评估，但不算原生像素直达显示面，也不能
成为添加额外后处理的理由。
