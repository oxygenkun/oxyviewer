# SCRFD-10G CPU 性能与流程优化（2026-09-20）

## 结论

在本机 release 构建、纯 Rust `tract` CPU 后端、640×640 输入上，SCRFD-10G 单次推理约
160–230ms。原流程的主要问题不是 NMS，而是推理次数：模型加载时先做一次全零 probe；开启
“检测小脸”时，24MP 照片还会执行 1 次整图加 9 次分块检测。因此普通照片可能无意义地支付
约十倍 detector 成本。

本次调整：

1. 移除模型加载阶段的全零推理。托管模型已在下载时验证固定 SHA-256，真实首次推理仍会验证
   九个输出 tensor 的布局，因此不会静默接受错误结果。
2. SCRFD/AdaFace 首次安装时把 `detectSmallFaces` 设为关闭。默认路径只运行一次整图 SCRFD；
   用户处理远景合影时仍可显式开启 3×3 重叠分块。
3. 保留每个分析 job 内的 analyzer 复用、前台浏览优先和逐资产取消点；没有通过增加并发抢占
   浏览资源。
4. 连续排队的 job 之间复用已解析的 analyzer；仅当队列真正空闲时释放 SCRFD/AdaFace，避免
   “释放后立刻重载”，同时不引入长期常驻模型缓存。

## 测量

命令：

```bash
cargo test --release -p oxy-faces profile_scrfd_10g_kps \
  --test reference_parity -- --ignored --nocapture
```

真实双人人像、同一模型与 640 输入（两次复测范围）：

| 指标 | 调整前 | 调整后 |
| --- | ---: | ---: |
| `ScrfdDetector::load` | 266ms | 95–117ms |
| 单次整图推理 | 约 159ms | 约 160–230ms（运行间波动） |
| 24MP 默认 detector pass | 10 | 1 |
| 24MP 默认 detector 估算 | 约 1.6–2.3s + resize | 约 0.16–0.23s + resize |

加载缩短约 56–64%；普通高分辨率照片的 detector 推理次数减少 90%。这里的 24MP 数字是基于
实测单次推理乘以确定的 view 数量，不是端到端图库吞吐；磁盘解码、AdaFace（按检测到的人脸
数量增长）、SQLite 提交和系统热状态仍会影响总耗时。

同一诊断还比较了动态输入尺寸：

| 输入 | warm 单次推理 | 检出脸数 |
| --- | ---: | ---: |
| 640 | 169–221ms | 2 |
| 512 | 111–116ms | 2 |
| 480 | 96–101ms | 2 |

512 在该样本上比 640 快约 31–50%，480 快约 40–57%。目前只有一张可再分发的真实测试照片，
不足以证明小脸、侧脸和遮挡场景的召回率不下降，因此产品仍保留 640 输入；这组数据只作为后续
建立多场景召回集后增加“速度优先”档位的候选依据。

## 保留的取舍

- 不让多个 SCRFD job 并行运行；人脸分析继续让位于浏览。
- 队列空闲时仍释放大型 analyzer，避免 AdaFace/SCRFD 常驻内存影响主浏览流程；相隔一段时间
  的重复启动会重新加载模型。这是内存优先的选择，后续若增加有界 idle warm cache，需要先测
  峰值内存。
- “检测远景小脸”开启后仍执行完整 3×3 分块，保持该显式高质量模式的召回率语义。
