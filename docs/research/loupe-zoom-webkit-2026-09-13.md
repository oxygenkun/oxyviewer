# macOS 大尺寸 CR3 缩放绘制回归

## 复现与修复

使用用户提供的 Canon EOS R5 CR3 的本地副本，完整内嵌 JPEG 为 8192×5464。
macOS Release / WKWebView、隔离 data/cache，真实照片和私有路径不入库。

73% 之后继续放大，显示像素开始偏离原图比例。原版本和修复版本的 DOM 均正确：

| 倍率 | 图片与 render 的实际尺寸（CSS px，四舍五入） |
| --- | --- |
| 50% | 4096×2732 |
| 73% | 5980×3989 |
| 91% | 7455×4972 |
| 100% | 8192×5464 |
| 150% | 12288×8196 |
| 200% | 16384×10928 |
| 400% | 32768×21856 |

在同一个 100% 画面，仅切换 `object-fit: contain` 与 `fill`，即可使飘带和
衣料细节在异常比例与正常比例之间切换。对照来自同一 JPEG 的未拉伸局部。
这将触发条件定位至 WKWebView 的大图 object-fit 绘制，而不是 RAW 解码尺寸
或缩放公式；没有据此推断 WebKit 内部的具体纹理限制。

Loupe 已按图片比例计算目标 CSS 宽高，因此直接 fill 这个画框即可保持比例。
修复只改变 Loupe 图片的 object-fit，保留布局、平移、导航器、源图和解码路径。
最终 Release 400% 实图及拖动正常，开发窗口额外验证 100% / 200% 的前后画面。

## 自动验证与性能边界

新增 `loupe-zoom` 隔离场景通过实际 wheel 事件检查上述七档尺寸，最终记录的
objectFit 为 fill。原版的几何探针同样通过，因此它不替代实际截图检查。

最终 Release 对同一真实夹具运行一轮缩放场景，以及三轮冷应用缓存 full 场景，
全部完成。未清除 OS 文件缓存：

| 指标 | 三次中位 | 三次最大 |
| --- | --- | --- |
| 打开目录到首屏双 rAF | 113 ms | 115 ms |
| 选中到完整 JPEG 解码就绪 | 323 ms | 443 ms |

首个可见预览即 full，三次中位低于 800 ms 冷预览预算。这里不代表 NAS 冷盘、
大目录或稳定分位数，也不是 GPU present 时间。原版单次 full 解码就绪为 283 ms，
样本不足以比较吞吐变化。

`pnpm check`、225 项前端测试、`pnpm build`、正式 Tauri Release 构建通过。
验证窗口使用独立应用标识，测试结束关闭测试实例。
