# NAS HIF 侧车写回：原因与优化方案 — 2026-10-15

后续：第一阶段已实现，见 [2026-10-16 验证](2026-10-16-embedded-metadata-sync-validation.md)。
本文保留优化前的调用链及原型证据；本地暂存仍未进入产品。

## 结论与范围

本次目录的主要成本是 SMB 上的 HIF 整文件重写及文件操作延迟。逐图启动
ExifTool 是确定存在的额外成本，但只复用进程不能解决当前 NAS 吞吐。
还确认了关键词重复追加和无变化仍重写的问题，优化应先保证重复同步的幂等性。

本轮进行了代码审计、真实文件复制品测速和候选方案实验，没有更改产品写入实现。
耗时是组件实验，不包含实际 WebView、Tauri IPC 和完整批量任务的全部成本。
交错复测中，候选方案九次总耗时从 2.728 s 降至 1.895 s，约缩短 30.5%；
不能把此前不同时段的中位数比值当作十倍产品提速。

## 样本与方法

- macOS arm64；挂载的 SMB 照片目录。公开记录省略机器名、共享地址和私人目录名。
- 目录含 1,545 张 HIF、146 个相邻 XMP。146 张可写照片共 1,153,916,312 字节，
  平均约 7.90 MB。不是所有 1,545 张照片都会进入侧车写回。
- 从带侧车的排序文件中选首、中、末三张，大小分别为 7,773,136、10,031,104、
  10,186,752 字节；用真实复制品比较本地 SSD 与同一 SMB 目录的写入。
- ExifTool 13.55，来自当前测试环境的 PATH。仓库托管下载仍固定为 13.59，
  本轮没有更换依赖，也不把 13.55 的数据当作所有提供者版本的保证。
- 每种顺序实验对三张文件各进行三轮真实变更，共九次写入；随后三次重复相同值。
  写入评分、颜色、旗标、一个普通关键词和一个层级关键词，检查实际内嵌结果。
- 每种方案重新建立复制品；不清 OS/SMB 缓存，不控制 NAS 服务端负载。
  所有样本均使用独立新文件，绝不使用原图的硬链接。
- NAS 写入仅发生于新建的隐藏测试子目录；测试结束自动删除。三张样本原图的
  SHA-256 前后相同；测试代码没有写入原始照片或原始 XMP。

完整逐次数据见[实验结果 JSON](2026-10-15-embedded-metadata-write-results.json)。

## 当前调用链

1. 前端 `useFolderMetadataSync.write` 对每个路径串行调用
   `syncMetadataToEmbedded([path])`，完成后才提交下一张。
2. 每次命令登记 job、创建一个 core worker，并等待该次操作完成。
3. `MetadataFacade::sync_metadata_to_embedded` 读取相邻 XMP，并把可编辑字段
   交给 `patch_embedded`。这里没有预先比较内嵌值是否已经相同。
4. `patch_embedded` 为每张图重新启动 ExifTool，使用 `-overwrite_original -P`；
   HIF 额外使用 `-api Compact=AllFormat`，保留 Sony 的颜色及空值约定。
5. 每张写入成功后，`MetadataService::run_edit` 清掉对应目录的文件摘要缓存，
   调用 metadata 的整目录失效，再请求该图的 Selected 优先级摘要刷新。
   `MetadataQueue::invalidate_directory` 还推进共享 request generation。
6. 整批结束后，前端再失效详情、浏览和预加载查询。

写入前后还会重复取得文件属性、检查并读取侧车、构建 fingerprint、读写 SQLite
投影。这些操作在 SMB 上有额外往返成本；本轮没有逐项 profile 它们，不能把所有
额外耗时归给这些操作，更不能仅凭整目录失效就声称已经测得 O(N²) 退化。

相关实现：

- [前端写回](../../apps/desktop/src/lib/hooks/useFolderMetadataSync.ts)
- [core 编辑用例](../../crates/oxy-core/src/metadata/service.rs)
- [ExifTool 参数和侧车解释](../../crates/oxy-core/src/metadata.rs)

ExifTool 官方说明 `-overwrite_original` 会用临时文件替换原文件，因此该路径
并非原地更新几字节。`-stay_open` 则用于避免每条命令重新加载程序。
参见[官方应用文档](https://github.com/exiftool/exiftool/blob/master/html/exiftool_pod.html)。

## 顺序组件实验

单位为毫秒；总计仅包含九次写入。常驻方案的单次进程预热另计，首次写入仍包含
写入模块的惰性加载。以下顺序实验不是随机对照。

| 位置 / 方案 | 单次中位数 | 最小—最大 | 九次总计 |
| --- | ---: | ---: | ---: |
| 本地，当前逐张启动参数 | 178.985 | 169.794—218.914 | 1,660.220 |
| 本地，复用进程、保持当前参数 | 12.873 | 11.122—114.044 | 224.245 |
| 本地，复用进程并替换关键词列表 | 13.511 | 10.936—122.967 | 229.470 |
| NAS，当前逐张启动参数 | 2,928.851 | 325.613—4,088.991 | 20,385.360 |
| NAS，复用进程、保持当前参数 | 2,513.108 | 1,288.796—3,435.147 | 22,179.776 |
| NAS，复用进程并替换关键词列表 | 3,945.120 | 152.720—7,241.357 | 31,581.074 |

单独执行 `exiftool -ver` 七次的中位数为 64.290 ms。这只测解释器和基础模块，
不包含 HIF 写入模块，不能把它当成全部启动成本。

本地数据表明进程复用收益明确；NAS 的中位数与整批耗时并未一致改善。
两种 NAS 常驻结果的差异也不能归因于关键词替换写法：服务端及缓存波动没有受控。
对这个目录，不能承诺仅增加 `stay_open` 就获得本地所见的数量级提速。

### 重复同步的两个独立问题

当前列表参数是先 `-TAG=`，再对每个值 `-TAG+=value`。真实 HIF 复制品上，
四次相同关键词写入后，普通和层级关键词都变为四份重复值。
原型把测试用的非空单项列表改成直接赋值后，每项仍只有一份；产品修复还需覆盖
多项列表替换及空列表清除。
这是正确性问题，不能为了速度继续沿用追加行为。

修正列表后，对相同评分、颜色、旗标和列表再次执行 ExifTool，三个文件仍全部
报告 updated。另用仓库 Sony HIF 复制品，删除普通/层级关键词并设置相同标记，
连续三次也都报告 updated。因此不能依赖当前 ExifTool 参数自动跳过无变化照片；
应用需要在调用 writer 前自己判断是否有必要写入。

## 本地暂存候选实验

原型先顺序读取 NAS 测试副本，在本地由常驻 ExifTool 修改，再顺序上传到 NAS
同目录的新临时文件。替换前重新检查测试源的 inode、大小和 mtime，并保留权限和
时间戳；最后替换测试副本。它仍然读写完整 HIF，只把容器处理留在本地。

顺序实验九次写入的中位数为 265.038 ms，总计 7,819.521 ms，范围
199.554—2,746.973 ms。各阶段中位数如下，阶段中位数不能直接相加当作总中位数：

| 阶段 | 中位数 ms |
| --- | ---: |
| 源属性 | 1.875 |
| NAS 顺序读取及本地复制 | 98.629 |
| 本地 ExifTool | 19.070 |
| NAS 顺序上传 | 122.014 |
| 复查、属性和替换 | 26.913 |

该方案在这轮样本中值得继续评估，但它执行在直接写入实验之后，受缓存和负载影响。
不能把中位数的比值直接宣传为产品提速倍数。

### 交错复测

随后对三张新复制品进行三轮、共九对比较，交替交换先后顺序。每对包含当前逐图
启动方式，以及本地暂存加常驻 ExifTool 的组合方案。两侧都改变评分以确保真实写入。

| 方案 | 单次中位数 ms | 最小—最大 ms | 九次总计 ms |
| --- | ---: | ---: | ---: |
| 当前逐图启动、直接 NAS 写入 | 306.761 | 280.302—323.222 | 2,728.081 |
| 本地暂存、常驻进程、上传后替换 | 233.842 | 141.709—252.574 | 1,895.445 |

组合方案在这段样本中九次总耗时缩短约 30.5%，全部九对均更快。但这一轮当前写法
本身也从此前数秒一张降到约 0.3 秒，证明 NAS/SMB/缓存状态的变化足以主导结果。
该比较同时包含进程复用、列表参数修正和网络访问方式变化，不能拆算单项收益。
它也不是长批次、冷缓存、网络拥塞或生产交互的性能保证。

原型没有完整实现文件恢复记录、跨平台权限/xattr 保留、强源证明或故障恢复；
也没有做显式 fsync、断网/崩溃测试和压缩图像数据完整性验证。
当前产品 ExifTool 路径也未增加显式 fsync。以上只能说明性能潜力，不能直接移入产品。

## 建议实施顺序

### 第一阶段：幂等、批处理与精确刷新

1. 先修正普通/层级关键词的替换参数，加入重复写入不增殖的真实 HIF 回归。
   保留 Sony HIF 的 compact XMP、颜色大小写与 0/None 标记语义。
2. 写前比较侧车与真正的内嵌可编辑字段，相同则计为 unchanged 并跳过 writer。
   不能使用被侧车覆盖后的详情/投影进行比较，否则会把需要同步的文件误判为相同。
   比较需归一化评分、空颜色、旗标和关键词列表；后续命中证明也要包含内嵌数据变化，
   不能只依赖被 `-P` 保留的 mtime、相同文件大小和侧车摘要。
3. 把整个文件夹写回移为 core 拥有的一个可观察 batch job，一个任务持有一个
   ExifTool session，先维持单个在途文件。前端只提交一次，展示逐文件结果/进度。
   单纯把路径数组一次传给现有命令仍会逐图启动 ExifTool，并在首个错误处停止，
   不能作为保持现有继续失败、取消和结果语义的完整优化。
4. 已写文件立即按路径失效，避免每张都清掉同目录其他照片的摘要/详情及推进共享
   generation。摘要回读和 UI 通知合并为有界批次；完成、失败及取消时都刷新已写部分。
   不为了提速移除源版本校验或延迟所有失效到整批成功之后。

常驻协议需要编号请求、每文件状态、stdout/stderr 并行排空、Unicode/换行参数处理
及提供者切换后的 session 重建。CoreRuntime 必须拥有 worker 和子进程生命周期；
取消停止下一文件，当前 native 写入需真实完成或报告超时/结果不确定，不得自动重试。

### 第二阶段：NAS 写入路径

若第一阶段后第一次批量写入仍受网络 I/O 限制，再把本地暂存方案接入
`oxy-core::files` 的安全操作和恢复机制。需要逐文件来源证明、同目录 staging、
替换前再验证、部分成功记录及断网/崩溃恢复，明确维护权限和扩展属性。
不要从前端直接复制/覆盖文件，也不要用缓存数据库承担用户文件恢复记录。

并发从 1 起步，只有代表 NAS 上的 Release 对照证明吞吐及交互都改善时才评估 2。
当前高度波动的数据不足以支持盲目增加 worker 或一次并发整个目录。

## 验收门槛

- 重复同步不追加重复关键词；相同字段不写原图；仅改侧车时只更新对应文件。
- 普通/层级关键词的清空、替换和 Unicode，Sony 颜色/旗标、JPEG/HIF 均保持一致。
- 失败后继续、取消后保留部分成功、提供者重新检测、shutdown 和不确定写入不重试。
- 暂存方案额外覆盖源并发修改、断网、磁盘满、恢复记录及权限/xattr/图像数据完整性。
- Release 核心与真实 WebView 对照，记录完整批量耗时、每文件分段、尾延迟及浏览交互；
  初次变更和全量无变化各测一轮，多轮交错排序，并说明 OS/NAS 缓存状态。
- 跨边界实现后运行 CONTRIBUTING 的前端、Rust、契约生成/漂移检查。

本次仅确认组件结果和原型潜力，尚未实施或验收上述产品优化。
