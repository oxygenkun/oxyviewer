# NAS HIF 内嵌写回有界并发 — 2026-10-16

## 结论与范围

在[单会话批处理](2026-10-16-embedded-metadata-sync-validation.md)之后，比较 1、2、4 个
独立 ExifTool 会话。产品默认采用 **2 路**：完整 core 对照有稳定的整批收益，4 路的
额外吞吐有限，而组件实验中的单文件尾延迟明显更高。没有把所有照片同时提交给
无限制进程，也没有更换 native 依赖或实现本地暂存替换。

本轮 macOS arm64、SMB、ExifTool 13.55；托管版本仍固定 13.59。使用此前同一三张
Sony HIF，每张建立四份独立副本，共 12 个写入路径、约 112 MB。一组不是 12 张
不同来源照片，也不是整个 146 张带侧车的目录。每种并发数测三轮、36 次真实变更；
顺序为 1/2/4、4/1/2、2/4/1。每个 case 重新建立副本、启动新会话，计入进程启动、
首次写入模块加载和会话关闭。不清 OS/NAS 缓存、不控制服务端负载。

## 组件实验

每个线程独占一个 stay-open 会话，只测 ExifTool 修改和关闭，不包含 native 比较、
core 资源投影、Tauri 或 WebView。单文件计时从该线程开始 execute 到该次回复。

| 并发数 | 三轮整批总计 ms | 每批中位数 ms | 单文件中位数 ms | 单文件 P95 ms |
| --- | ---: | ---: | ---: | ---: |
| 1 | 5,679.850 | 1,883.396 | 146.116 | 296.967 |
| 2 | 4,917.158 | 1,635.828 | 245.823 | 416.745 |
| 4 | 5,034.024 | 1,671.063 | 514.139 | 662.949 |

2 路整批耗时比 1 路减少 13.4%；4 路没有继续改善。并发可以提高吞吐，同时延长
单文件的完成时间；不能把整批加速描述为每张照片都更快。

## Release core 对照

复用 [embedded_sync_latency.rs](../../crates/oxy-core/examples/embedded_sync_latency.rs)
的 `--concurrency` 模式。它通过公开 `sync_to_embedded_with_options` 运行真实 core
batch，包含路径/文件身份观察、真实内嵌比较、写入、精确失效、刷新准入、所有子任务
及会话 join；每次真实变更后再测一次完全相同的同步。

写入期间每 50 ms 以闭环方式读取一次当前目录首页。主要命中已经建立的 browse
snapshot，因此这是缓存目录读取的 backend 争用覆盖，**不是**全新 NAS 目录的冷枚举、
WebView 首屏或真实 UI P95。整批计时至 benchmark 收到最终结果，包含同一循环中
可能正在执行的最后一次首页读取。最终测量期间没有同时运行编译检查。

| 并发数 | 36 次真实变更总计 ms | 12 张一批中位数 ms | 36 次未变化检查总计 ms |
| --- | ---: | ---: | ---: |
| 1 | 10,001.042 | 3,392.492 | 670.978 |
| 2 | 8,221.998 | 2,739.948 | 436.279 |
| 4 | 7,579.507 | 2,534.010 | 340.649 |

2 路比 1 路减少 17.8% 的真实变更耗时；4 路比 2 路再少 7.8%。结合组件尾延迟、

最大为 53.166/51.831/46.046 ms；每个 case 首次读取的数十毫秒不能被热缓存 P95 掩盖。

## 实现和生命周期

- 一个 CoreRuntime worker 拥有 scoped dispatcher 和 writer，批次之间仍由应用独占
  gate 串行，避免多批任务叠加并发。每路独占一个惰性 ExifTool session 和两个 pipe reader。
- Dispatcher 顺序观察路径，经无缓冲 channel 准入；全局 queue 锁不包住文件或 SQLite
  操作。相同 canonical target 保留首个路径、后续计为 skipped。硬链接和大小写别名
  使用文件身份的先后完成凭据串行，保留各自侧车及输入顺序；取消可以解除等待。
- 计数、进度、失效和摘要刷新集中汇总，完成顺序允许不同，失败列表仍按原输入顺序。
  默认最多两张在途；Host-side options 仅允许 1–4，供受限资格验证，不新增 IPC 或设置。
- 取消停止新写入，所有已进入 native 的操作完成后才回复。一路失去确认会停止整批
  新准入；其他在途成功仍记入最终结果，不重放未知结果，不自动拉起替代 writer。
- coordinator 退出前 join 所有线程/进程/pipe reader。shutdown deadline 到达时，
  活跃 native 操作仍报告未 join。若线程在执行期间 panic，停止后续准入后才释放文件顺序凭据。

回归覆盖同时进入两个独立 native 子进程、取消后的两个部分成功、shutdown 不伪报
join、一路断协议后保留另一路成功、不重试、canonical 别名去重、硬链接输入顺序、
并发数越界拒绝，以及之前的幂等、数组、Unicode、分页和精确失效回归。

## 检查和实际桌面验证

通过 `pnpm check`、`pnpm test`（75 文件 / 444 项）、wrapper 的 Release 前端 build
和 macOS `.app` 打包、contracts check、fmt、包含 contracts 的 workspace Clippy
及 workspace 测试；core 共 308 项通过，8 项按既有夹具要求忽略。

首次桌面尝试遇到 Mac 锁屏；用户手动解锁后，在最终 macOS Release WKWebView
中完成验证。使用独立 core-v2 状态和同一 SMB 目录的新临时子目录，建立 12 份 HIF
及侧车副本，从文件夹右键执行：

1. 在界面显示 0/12 时点击取消，当前两个在途写入完成后显示“已取消后续写入，
   写入 2，未变化 0，失败 0”。磁盘上恰有两份带新关键词，其余十份的字节与源副本一致。
2. 再次执行，界面先显示“未变化 2”，最终为“写入 10，未变化 2，失败 0”。
   先前写入的两份 SHA-256 与 mtime 保持不变；十二份均核对评分、颜色、旗标及关键词。
3. 第三次显示“写入 0，未变化 12，失败 0”；全部十二份 SHA-256 和 mtime 不变。

十二份的压缩图像 packet 与对应源图一致，三张源 HIF 和原始 XMP 的 SHA-256
前后相同。测试后关闭自启应用、清理独立状态和 NAS 副本。记录见
[ui.json](2026-10-16-embedded-metadata-concurrency-ui.json)。这是实际 IPC/事件/可见
交互与磁盘结果的验证，没有把自动化操作时间当作 WebView 延迟测量。

## 限制

这些结果来自同一挂载目录的小批次、三种照片内容的重复副本。SMB 服务端、缓存和
其他读写的变化仍会主导结果；不能推算整批 146 张的耗时或所有 NAS 的最佳并发数。
没有测量 Windows/Linux、断电耐久性或不同格式的大批次。ExifTool 仍会重写 HIF
整文件；本地暂存替换仍需 files 的来源证明、属性保留和恢复机制。
